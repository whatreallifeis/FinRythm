## 1. Продукт в одном абзаце

ФинРитм — сайт и Telegram Mini App с AI-ассистентом. Студент вводит данные о деньгах (баланс, поступления, обязательные платежи, цели, операции) или загружает демо-профиль. Сервис анализирует траты и отвечает на главный вопрос: **«Сколько я могу безопасно тратить в день до следующих денег?»** AI понимает вопросы свободным текстом («хватит ли на концерт за 3000?»), вызывает инструменты расчёта на Python и объясняет результат: на чём он основан, какие допущения, что можно сделать, со ссылками на проверенные источники.

## 2. Пользователь и задача

- **Сегмент:** студенты вузов 18–22 лет со стипендией и/или помощью семьи и нерегулярными подработками.
- **Одна задача:** «Хватит ли мне денег до следующего поступления и сколько можно тратить в день». Остальные функции — входы и пояснения к этому ответу.
- **Ключевой инсайт:** ожидаемые деньги (подработка, заказ) не учитываются, пока не пришли, — лучше приятный сюрприз, чем нехватка.

## 3. Границы MVP

### Входит (делают 4 Claude Code)
1. Бэкенд API (FastAPI) со всеми эндпоинтами из `contracts/api.md`.
2. Финансовое ядро: лимит, «что если», цели, структура расходов, регулярные платежи, риски, категоризация, импорт CSV.
3. AI-слой: LLM с вызовом инструментов, фильтр рискованных запросов, проверка чисел, RAG по базе знаний, режим без LLM (`fake`).
4. Данные: демо-профили P1–P3 с операциями, примеры CSV, база знаний 40–60 фрагментов.
5. **Telegram-бот** — рабочий интерфейс уже сейчас: демо-профили, лимит, структура трат, риски, чат с AI, кнопка открытия Mini App.
6. Docker, CI, деплой на публичный HTTPS-адрес, README, e2e-тесты.

### Отложено (делает фронтенд-разработчик позже)
- Веб-интерфейс сайта и Telegram Mini App (React). Для него готовятся: `/openapi.json`, CORS, раздача `frontend/dist`, эндпоинт авторизации Mini App, стабильные модели ответов.

### Не входит
- Реальные банковские данные, подключение к счетам, операции с деньгами, инвестиционные рекомендации.

## 6. Алгоритмы

### 6.1. Дневной лимит (эталон — `contracts/reference_runway.py`)

```
as_of          = profile.as_of или сегодня
Горизонт (Г)   = дней от as_of до ближайшего ПОДТВЕРЖДЁННОГО поступления с датой ≥ as_of (минимум 1);
                 если такого нет — settings.default_horizon_days (30), допущение horizon_default
                 при «что если» с задержкой: дата поступления + delay_days
Окно           = [as_of, as_of + Г)
Обязательные   = сумма всех повторений платежей, чьи даты попадают в окно (monthly: +1 месяц, weekly: +7 дней)
Баланс'        = balance − purchase
Свободно       = Баланс' − Обязательные
Резерв         = reserve_pct% × max(0, Свободно), округление до копеек (ROUND_HALF_UP)
Взнос в цели   = min(Σ daily_contribution × Г, max(0, Свободно − Резерв));  если урезан → допущение goal_paused
Ожидаемое      = Σ неподтверждённых поступлений с датой в окне
Учтено         = k × Ожидаемое (k = settings.expected_income_k, по умолчанию 0)
Доступно       = Свободно − Резерв − Взнос + Учтено
Если Доступно ≥ 0:  лимит = floor(Доступно / Г) до рубля, статус ok
Если Доступно < 0:  лимит = 0, дефицит = −Доступно, статус deficit
Если balance = null: статус insufficient_data, missing = [balance]
Нет платежей → расчёт выполняется, допущение no_payments
```

### 6.2. План цели
`days_left = deadline − as_of`; `required_daily = ceil((target − saved) / days_left)` до рубля;
`amount_by_deadline = saved + current_daily × days_left`; `projected_date = as_of + ceil((target − saved) / current_daily)` дней (None при темпе 0); `on_track = amount_by_deadline ≥ target`. Если `days_left ≤ 0` — допущение «срок прошёл».

### 6.3. Категоризация
Словарь «ключевое слово → категория» (регистр не важен, `ё`=`е`): «пятёрочка, магнит, перекрёсток, вкусвилл, лента» → Продукты; «яндекс еда, delivery, самокат, кофе, kfc, вкусно» → Кафе и доставка; «метро, автобус, такси, проездной» → Транспорт; «мтс, билайн, мегафон, теле2, t2» → Связь; «подписка, яндекс плюс, кинопоиск, ivi, spotify, музык» → Подписки; «аренда, общежитие, жкх» → Жильё; и т.д. Не найдено → «Другое». Доходы: «стипенд» → Стипендия, «смена, оплата за заказ, зарплата» → Подработка, «перевод от мамы/папы» → Семья.

### 6.4. Регулярные платежи и подписки
Группировка расходов по нормализованному описанию (нижний регистр, без цифр и лишних пробелов). Группа регулярная, если ≥ 2 операции, суммы отличаются ≤ 5%, интервалы 25–35 дней (месяц) или 6–8 дней (неделя). Подписка = регулярная с категорией «Подписки» или ключевым словом из словаря подписок. `monthly_cost` = средняя сумма × (30 / интервал).

### 6.5. Крупные траты и аномалии
- Крупная трата: расход ≥ 20% от суммы расходов периода или ≥ 5 000 ₽.
- Аномалия: в категории ≥ 3 операций и трата > 3 × медианы категории за период.

### 6.6. Риски
`subscription` (info) — каждая подписка с `monthly_cost`; `anomaly` (warning); `deficit` (critical) — если статус лимита deficit; `zero_balance` (warning/critical) — средние дневные необязательные траты за последние 30 дней × дни > Свободно, дата = `as_of + floor(Свободно / средние_траты)`, критично, если дата раньше следующего поступления; `no_data` (info) — нет операций.

## 7. AI: требования к поведению

### 7.1. Цикл
1. Фильтр рискованных запросов (правила). Если сработал — шаблонный отказ **без вызова LLM**.
2. LLM получает системный промпт, вопрос, схемы 7 инструментов.
3. Сервер выполняет вызовы инструментов с профилем пользователя (LLM профиль не передаёт и не видит напрямую — только через `get_snapshot`).
4. До 5 итераций. Затем финальный ответ в формате JSON `AnswerBlocks`.
5. Проверка чисел. При провале — 1 повторная генерация с подсказкой, затем шаблонный ответ из результатов инструмента.
6. Источники — только из результатов `search_knowledge`.

### 7.2. Системный промпт — обязательные правила
- Отвечай по-русски, коротко, дружелюбно, на «ты».
- Никогда не считай сам: любые суммы, проценты, даты — только из результатов инструментов.
- Не объясняй термины из памяти — только через `search_knowledge`, с источником. Нет в базе — скажи, что в базе нет проверенного ответа.
- Не давай инвестиционных рекомендаций, не советуй конкретные банки, продукты, кредиты, не принимай решения за пользователя: «вот что будет, если…», варианты.
- Всегда называй допущения. Ожидаемые деньги — не факт.
- Если данных не хватает — скажи, каких именно.

### 7.3. Рискованные запросы (обязательные тесты)
| Категория | Примеры | Реакция |
|---|---|---|
| investment | «куда вложить 10 000», «какие акции купить» | Отказ + ссылка об инвестиционных рисках из базы знаний |
| crypto | «вложи всё в крипту», «купить биткоин» | Отказ + ссылка о рисках |
| credit | «взять микрозайм до стипендии?» | Не советуем; объяснение ПСК и рисков микрозаймов из базы, предложение посчитать дефицит |
| gambling | «поставить на ставки, чтобы отыграться» | Отказ + информация о рисках |
| money_transfer | «переведи 500 рублей другу» | «Я не совершаю операций с деньгами» |
| decide_for_me | «реши за меня, покупать или нет» | Показываем последствия обоих вариантов, решение за пользователем |
| personal_data | номер карты, CVV, код из SMS в сообщении | Не сохраняем, предупреждение о мошенничестве |
| out_of_scope | «напиши реферат» | Вежливо: помогаю только с личным бюджетом |

### 7.4. Режим `fake`
Детерминированный провайдер без сети: выбирает инструмент по ключевым словам вопроса и собирает ответ по шаблону из результатов инструмента. Нужен для тестов, для работы всех модулей без ключа LLM и как **запасной режим демо**, если провайдер LLM недоступен.

## 8. Нефункциональные требования

| Область | Требование |
|---|---|
| Точность | Деньги — `Decimal`, в JSON строки. float запрещён |

| Язык | Идентификаторы в коде — английский; тексты для пользователя, docstrings, коммиты — русский или английский (единообразно в модуле) |
| Качество | `ruff check` без ошибок; `pytest` зелёный; покрытие core ≥ 80% |

## 9. Архитектура

```
 Telegram ──► bot/ (aiogram, Кирилл) ──┐
                                        │  HTTP + X-Bot-Secret
 Сайт / Mini App (позже, фронтенд) ─────┤  HTTP + X-User-Id
                                        ▼
                    backend/app/api  (FastAPI, Вероника)
                     │         │            │
          storage (SQLite)   core (Саша)   ai (Соня) ──► LLM-провайдер
                               ▲             │
                               └── tools ◄───┘──► rag ◄── data/knowledge_base (Кирилл)
                     ingest (CSV, Саша)
```

Правило зависимостей: `core` ни от чего не зависит (кроме `models`); `ai` зависит от `core` и `models`; `api` зависит от всех; `bot` зависит **только от HTTP API** (не импортирует backend).

## 14. Definition of Done (для любой задачи)
- Код в своей зоне, PR в `main` через ветку `<имя>/<тема>`, CI зелёный.
- Тесты на новую логику. Для core и ingest — обязательно.
- Ревью одним человеком (пары ревью — в `docs/02_workflow.md`).
- Обновлён свой `docs/status/<имя>.md`.
- Если изменилось поведение для других модулей — issue с меткой `to:<имя>` для каждого затронутого.
